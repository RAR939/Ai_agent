# Роль 1: тимлид

*ИИ-агент «Анализатор учебных чатов»: инструкции по задачам*

## Кратко о роли

Вы отвечаете за то, чтобы пять модулей, написанных разными людьми, собрались в один работающий агент. Основной риск проекта не в сложности отдельных модулей, а в несовпадении форматов данных между ними. Поэтому ваша главная работа происходит в самом начале (контракты данных) и на стыках (точки интеграции).

| Параметр | Значение |
|---|---|
| Роль | Роль 1: тимлид |
| Ваши задачи | 0.1 репозиторий и процесс, 0.2 контракты данных, 0.3 синтетический чат (вместе с ролью 2), 0.4 словари и конфиг (вместе с ролью 4), 0.5 окружение и выбор модели (вместе с ролью 5), Q1 разметка, Q5 заделы под статью, Q6 отчёт и демонстрация |
| Кто ждёт вас | Все. Задача 0.2 блокирует работу ролей 2–6, поэтому делайте её первой |
| От кого зависите | Ни от кого на старте. Для 0.3 нужна роль 2, для 0.4 роль 4, для 0.5 роль 5 |
| Если команда из 5 человек | Вы берёте и задачи роли 5 (MCP-сервер и агентный цикл) |

### 0.1. Репозиторий и процесс

**Цель.** Чтобы любой участник мог за 10 минут клонировать проект, поставить окружение и запустить пустые тесты.

#### Шаги

1. Создайте репозиторий (GitHub или GitLab). Основная ветка `main` защищена: прямые коммиты запрещены, слияние только через pull request с одним одобрением.
2. Создайте структуру папок из раздела «Общие правила» ниже. В каждой папке модуля положите файл `README.md` с одной строкой «что здесь лежит» и пустой `__init__.py` там, где это Python-пакет.
3. Заведите `.gitignore`: `data/`, `*.db`, `*.sqlite`, `chroma/`, `.env`, `.venv/`, `__pycache__/`, `*.html` внутри `data/`. Проверьте командой `git status`, что после копирования туда тестового экспорта он не отображается.
4. Положите `requirements.txt` с зафиксированными версиями. Стартовый набор: `ollama`, `chromadb`, `rank-bm25`, `sentence-transformers`, `pydantic`, `dateparser`, `recurring-ical-events`, `icalendar`, `openpyxl`, `pandas`, `beautifulsoup4`, `lxml`, `pymorphy3`, `mcp[cli]`, `streamlit`, `streamlit-calendar`, `plotly`, `pyvis`, `pytest`, `pyyaml`, `python-dotenv`.
5. Добавьте `tests/test_smoke.py` с одним тестом `assert True` и настройте автозапуск `pytest` на каждый pull request (GitHub Actions: шаг установки зависимостей и шаг `pytest`).
6. Напишите `docs/CONTRIBUTING.md` на одну страницу: правила веток, шаблон описания pull request, правило «ревьюит не автор», определение «готово».

#### Результат

- Репозиторий со структурой, `.gitignore`, `requirements.txt`, автозапуском тестов и `CONTRIBUTING.md`.

#### Как проверить, что готово

- Двое других участников клонировали репозиторий и успешно выполнили `pytest` на своих ноутбуках.
- Попытка запушить в `main` напрямую отклоняется.

> **Частые ошибки.** добавить `.gitignore` позже, когда данные уже попали в историю git (удалить их оттуда трудно, а чужие сообщения публиковать нельзя); не зафиксировать версии зависимостей, из-за чего у разных людей работает по-разному.

### 0.2. Контракты данных (самая важная задача)

**Цель.** Описать один раз форматы данных, которыми обмениваются модули, чтобы роли 2–6 могли работать параллельно, не дожидаясь друг друга.

**Что нужно до начала.** Ничего. Но перед финализацией обсудите схемы со всеми пятью участниками на коротком созвоне (30–40 минут) и получите от каждого явное «согласен».

#### Шаги

1. Создайте `src/schemas.py` с моделями pydantic (берите из документа «Контракты данных», раздел 3). Каждое поле снабдите комментарием: что означает, пример значения, может ли быть пустым.
2. Создайте `docs/contracts.md`: для каждой модели одна страница с примером JSON и перечнем, кто её создаёт и кто потребляет.
3. Зафиксируйте идентификаторы. Идентификатор сообщения: `<chat_id>:<номер_сообщения_в_экспорте>`, например `elektro:1042`. Идентификатор чанка: `<chat_id>:<первый_msg>-<последний_msg>`. Идентификатор дедлайна: целое число из SQLite.
4. Зафиксируйте вложения: тип `AttachedFile` (идентификатор `<id сообщения>:f<номер>`, имя для показа обезличено, путь относительно папки чата), поле `attachments` в `Message` и `Deadline`, три способа привязки файла к дедлайну (`bind`: `same_message`, `same_author_near`, `reply_context`). Файлы остаются локальными и не попадают в репозиторий.
5. Зафиксируйте время: везде хранится строка ISO 8601 с часовым поясом `+03:00` (Москва). Любая функция, принимающая время, принимает именно её.
6. Зафиксируйте роли авторов: `starosta`, `teacher`, `student`, `unknown`. Дисциплины: ключ из `config.yaml` (латиницей, например `elektro`, `models`), а не русское название.
7. Разошлите схемы, соберите замечания, внесите правки, получите от всех подтверждение, затем «заморозьте»: с этого момента изменения только через pull request с пометкой `contract-change` и уведомлением в общем чате.

Готовый черновик всех схем, сигнатур функций, схемы базы и конфигов лежит в документе «Контракты данных». Ваша работа: скопировать код в `src/schemas.py`, доработать по замечаниям команды, добавить проверки (время с поясом) и тест `tests/test_contracts.py`.

#### Результат

- `src/schemas.py`, `docs/contracts.md`, подтверждения от пяти человек.

#### Как проверить, что готово

- Каждый участник может ответить на вопрос «что мой модуль принимает и что возвращает» ссылкой на конкретную модель в `schemas.py`.

> **Частые ошибки.** оставить поля «на потом» без описания; разрешить каждому добавлять поля «для себя» без уведомления; использовать разные форматы времени (с поясом и без пояса) в разных модулях.

### 0.3. Синтетический мини-чат (вместе с ролью 2)

**Цель.** Дать всем общий тестовый материал, пока реальные чаты проходят согласование. Без него роли 3, 4, 5 и 6 будут ждать парсер.

#### Шаги

1. Роль 2 даёт образец HTML-разметки из реального экспорта Telegram (одно-два сообщения без личных данных).
2. Вы с ролью 2 сочиняете 50–80 вымышленных сообщений по двум-трём дисциплинам. Обязательно включите: новый дедлайн («Лабу 2 сдаём до пятницы»), перенос («перенесли на 5 ноября»), отмену, ответ на сообщение («а когда сдавать?» — «до среды»), размытый срок («на днях»), срок через занятие («на следующей паре по электротехнике»), шум («ахах», стикеры), пересланное сообщение, сообщения старосты, преподавателя и студентов.
3. Роль 2 оформляет это в тот же HTML-формат, что даёт Telegram, и кладёт в `tests/fixtures/mini_chat/`.
4. Добавьте вложения: 8–10 сообщений с файлами. Положите в `tests/fixtures/mini_chat/files/` маленькие вымышленные файлы (пустой PDF и DOCX на пару килобайт) и ссылки на них в HTML так, как это делает Telegram. Обязательно: файл в том же сообщении, что дедлайн; файл от того же автора через пять минут; файл в ответе на «когда сдавать?»; файл другого автора в это же время (не должен прикрепляться); файл через час (не должен); перенос с новым файлом; сообщение с файлом без подписи; сообщение, где файл не выгружен.
5. Рядом положите файл `tests/fixtures/mini_chat_expected.json`: для каждого сообщения-дедлайна ожидаемый результат (дисциплина, задание, дата, действие, `files_expected`: список id файлов, которые должны быть прикреплены). Это первая версия эталона.

#### Результат

- Папка `tests/fixtures/mini_chat/` и файл ожидаемых результатов.

#### Как проверить, что готово

- Роль 2 подтвердила, что структура совпадает с реальной; роль 4 нашла в наборе все виды сроков, которые будет разбирать.

### 0.4. Словари и конфиг (вместе с ролью 4)

**Цель.** Собрать в одном файле всё, что меняется без правки кода.

#### Шаги

1. Создайте `config/config.yaml` с разделами: `models` (названия LLM, эмбеддингов, реранкера, температура), `retrieval` (размер окна чанка, перекрытие, число кандидатов, порог релевантности), `tracker` (ключевые слова предфильтра, порог уверенности, порог похожести заданий), `schedule` (даты начала и конца семестра, правило чётности), `paths`.
2. Составьте `config/disciplines.yaml`: ключ, официальное название, сокращения и разговорные варианты. Пример: `elektro: {name: "Электротехника", aliases: ["электротех", "электра", "ЭТ"]}`. Список собирают участники команды по реальным чатам.
3. Составьте `config/roles.yaml` (файл с реальными именами в репозиторий не кладём, только шаблон): староста, преподаватели и участники с метками. Заполняет роль 2 локально.

#### Результат

- Три файла конфигурации, загружаемые одной функцией `load_config()`.

#### Как проверить, что готово

- Смена модели или порога в конфиге меняет поведение без правки кода.

### 0.5. Окружение и выбор модели (вместе с ролью 5)

**Цель.** Выяснить, какая модель реально работает на самом слабом ноутбуке в команде, до того как на неё будут завязаны промпты.

#### Шаги

1. Каждый установил Ollama и модели по инструкции из раздела «Окружение у каждого».
2. Самый слабый ноутбук прогоняет замер: 10 одинаковых вопросов с контекстом около 1500 токенов. Записать: время до первого токена, общее время ответа, пиковое использование памяти (диспетчер задач).
3. Сравнить `qwen3:8b`, `qwen3:4b` и одну запасную модель. Критерий выбора: ответ на вопрос с контекстом занимает до 30 секунд и ноутбук не уходит в своп.
4. Проверить вызов функций: дать модели два простых инструмента и три вопроса. Если модель не вызывает инструменты, роль 5 должна знать об этом сразу.
5. Записать итог в `docs/model_decision.md`: выбранная модель, цифры замеров, запасной вариант.

#### Результат

- `docs/model_decision.md` с цифрами; модель прописана в `config.yaml`.

#### Как проверить, что готово

- Инструкция запуска проверена на всех ноутбуках команды.

> **Частые ошибки.** мерить скорость на мощном ноутбуке и выбирать модель по нему; забыть, что на защите ноутбук может работать от батареи (производительность падает).

### Q1. Организация разметки тестового набора

**Цель.** Получить 30–50 размеченных сообщений, по которым роли 2 и 4 будут считать точность. Без этого все цифры в отчёте будут «на глаз».

#### Шаги

1. Напишите `docs/annotation_guide.md` на 1–2 страницы. Для каждого поля: определение, три примера «да» и три «нет». Поля: есть ли срок (да/нет), дисциплина, тип работы, задание, срок как написано, действие (новый/перенос/отмена), размытый ли срок, **какие файлы относятся к заданию** (список id; правило: файл относится к заданию, если его прислали вместе с объявлением, рядом от того же автора или в ответ на вопрос о задании).
2. Разберите заранее трудные случаи и запишите решения: «до пятницы» отвечает на вопрос «когда сдавать Лаб.2?» (разметить как срок для Лаб.2); «кто-нибудь сделал ДЗ?» (срока нет); «ну сдавать надо скоро» (срок есть, размытый).
3. Выберите 40 сообщений из обезличенных чатов: примерно 20 с дедлайнами, 10 с переносами или отменами, 10 без дедлайна, но с похожими словами («сдать» в другом смысле, «до» как предлог).
4. Раздайте так, чтобы каждый из шести размечал свои 10–15 сообщений, а 20% набора (8 сообщений) разметили двое независимо друг от друга.
5. Разметка идёт в общую таблицу (Google Таблицы или CSV в репозитории). Не показывать размечающему ответ модели.
6. Соберите расхождения на двойных сообщениях, обсудите, дополните руководство и посчитайте согласованность (доля совпавших решений; для статьи позже каппа Коэна: `sklearn.metrics.cohen_kappa_score`).
7. Положите итог в `eval/gold_deadlines.jsonl`, по одному объекту на строку (поле `files_gold` с id файлов).

#### Результат

- Руководство по разметке и `eval/gold_deadlines.jsonl` на 30–50 сообщений.

#### Как проверить, что готово

- На двойных сообщениях согласованность не ниже 80%; расхождения разобраны и учтены в руководстве.

### Q5. Заделы под статью

**Цель.** Сделать так, чтобы после сдачи курсовой код не пришлось переписывать для научной работы.

#### Шаги

1. Проверьте на ревью, что ответ модели и метка человека хранятся в разных полях (`LabelRecord`).
2. Проверьте, что каждый результат извлечения пишется в лог с версией промпта (`prompt_version` из конфига) и названием модели.
3. Проверьте, что тематика (дедлайны) определяется схемой и промптами, а не жёстко зашита в логику: чтобы потом заменить схему на гуманитарную (жанр сообщения, тип выражения срока, определённость).
4. Собирайте в `docs/article_notes.md` наблюдения по ходу работы: какие формулировки сроков встречаются, где модель ошибается. Это материал для раздела «Результаты».

#### Результат

- Заметки в `docs/article_notes.md`; ревью по трём пунктам пройдено.

### Q6. Отчёт и демонстрация

**Цель.** Подготовить текст отчёта и безотказный сценарий показа.

#### Шаги

1. Структура отчёта: постановка задачи и предметная область; обзор аналогов (NotebookLM, Folk, шаблоны n8n, RAG-ассистенты курсов); архитектура с рисунком; данные и этика (согласия, анонимизация); реализация по модулям; оценка с таблицами; ограничения; выводы.
2. Каждый участник пишет раздел о своём модуле на 1–2 страницы и присылает вам. Вы сводите, унифицируете терминологию, добавляете введение, выводы и сравнение с аналогами.
3. Сценарий демонстрации (отрепетировать минимум три раза на том ноутбуке, где будет показ): (1) в чат приходит «Лаб.2 перенесли на 5 ноября»; запускаем обработку; в календаре дедлайн сдвинулся, видна история переноса со ссылкой на сообщение. (2) Вопрос «что говорили про рубежку?» — ответ с источниками. (3) Вопрос, ответа на который нет в данных, — агент честно отвечает «не нашёл». (4) Загрузка расписания и вопрос «когда следующая лаба по электротехнике?». (5) Карточка задания «Лаб.2»: срок, история переноса, прикреплённые файлы, блок «Что говорили»; вопрос «какие материалы к Лаб.2?» и «что нужно в отчёте по Лаб.2?». (6) Перенос с новым файлом: после обработки в карточке появляется второй файл.
4. Подготовьте запасной вариант: запись экрана с успешным прогоном на случай, если на защите что-то откажет, и заранее обработанные данные, чтобы демонстрация не зависела от скорости модели.

#### Результат

- Отчёт, презентация, запись демонстрации, ноутбук с проверенным запуском.

## Как вести проект

### Точки интеграции

Это моменты, когда нужно собрать всё вместе и проверить. Не откладывайте их на конец: ошибки на стыках находятся только так.

| № | Что должно работать | Какие задачи нужны |
|---|---|---|
| 1 | Синтетический чат → парсер → индекс → вопрос → ответ с источником в консоли | 0.x, 2.4, 3.1–3.5 |
| 2 | Трекер заполняет базу из реального чата, расписание загружено | 2.5, 4.1–4.9 |
| 3 | Агент сам вызывает инструменты MCP | 5.1–5.4 |
| 4 | Интерфейс показывает всё целиком, подтверждения работают | 5.3, 6.2–6.6 |
| 5 | Замеры, исправления, отчёт, репетиция демонстрации | Q3, Q6, 6.8 |

### Короткая синхронизация

- Раз в несколько дней — 15 минут. Каждый отвечает на три вопроса: что сделал, что делает, что мешает.
- Если кто-то пишет «заблокирован» — вы в тот же день выясняете причину и либо снимаете блок, либо даёте заглушку.
- Ведите доску задач (GitHub Projects или Trello) по номерам задач из таблицы: «не начато», «в работе», «на ревью», «готово».

### Риски и что с ними делать

| Риск | Что делать |
|---|---|
| Данные попали в репозиторий или чужим людям | Сразу убрать из истории git, сообщить команде; сырые экспорты хранить только у роли 2, остальные работают на обезличенных файлах |
| Модель 8B слишком медленная | Перейти на 4B, сократить контекст (4 чанка вместо 5), включить порог релевантности, чтобы не вызывать модель впустую |
| Модель плохо вызывает инструменты | Роль 5 включает запасной план: маршрутизация правилами, модель только формулирует ответ |
| Не сходятся форматы между модулями | Любое несоответствие — через pull request в `schemas.py`; не лечить адаптерами внутри модулей |
| Один человек не успевает | Перераспределить: роль 6 берёт тесты роли 2, роль 3 помогает с оценкой |

## Контракты вашей роли

Это та часть единого контракта данных, которая касается именно вас: что вы принимаете, что отдаёте, какими типами и функциями. Ответственность двойная: вы соблюдаете чужие форматы на входе и гарантируете свой формат на выходе. Полный документ называется «Контракты данных».

#### Общие соглашения (действуют для всех)

- Время всегда строка ISO 8601 с поясом `+03:00`, например `2026-10-21T14:03:00+03:00`. Дата без часа получает `23:59:00`.
- Идентификаторы: сообщение `elektro:1042`, чанк `elektro:1040-1051`, дедлайн, занятие и ожидающая запись целое число из SQLite.
- Роли авторов `starosta`, `teacher`, `student`, `unknown`; дисциплины это ключи из `config/disciplines.yaml` латиницей.
- Нет значения: `None` или `null`, не пустая строка. Ошибки в инструментах возвращаются как `{"error": "текст"}`.
- Типы и сигнатуры менять нельзя. Нужно изменение: pull request с пометкой `contract-change` и сообщение в общий чат. Полный текст контракта: документ «Контракты данных».

```
from pydantic import BaseModel, Field
from typing import Literal, Optional

# ---------- общие типы ----------
Role = Literal["starosta", "teacher", "student", "unknown"]
Kind = Literal["lab", "hw", "midterm", "exam", "other"]
Status = Literal["active", "moved", "done", "cancelled", "pending"]
LessonType = Literal["lecture", "seminar", "lab", "other"]
ISO = str   # "2026-10-21T14:03:00+03:00", всегда с поясом +03:00

# ---------- роль 2 -> все ----------
class AttachedFile(BaseModel):
    id: str                   # "elektro:1042:f1"
    msg_id: str               # сообщение, к которому приложен файл
    name: str                 # имя для показа, обезличенное: "lab2_elektro.pdf"
    ext: str                  # "pdf", "docx" (нижний регистр, без точки)
    size_bytes: int
    path: str                 # относительно data/raw/<chat>/ : "files/lab2.pdf"
    bind: Optional[Literal["same_message", "same_author_near",
                           "reply_context"]] = None   # как привязан к дедлайну

class Message(BaseModel):
    id: str                   # "elektro:1042"
    chat: str                 # "elektro"
    ts: ISO
    author: str               # метка: "STAROSTA", "STUDENT_7", "TEACHER_2"
    role: Role
    text: str                 # обезличенный текст, не пустой
    reply_to: Optional[str] = None   # id исходного сообщения
    forwarded: bool = False
    src: str                  # "messages2.html#message1042"
    attachments: list[AttachedFile] = []   # только документы

# ---------- роль 3 ----------
class Chunk(BaseModel):
    id: str                   # "elektro:1040-1051"
    chat: str
    msg_ids: list[str]        # по порядку
    ts_from: ISO
    ts_to: ISO
    roles: list[Role]         # уникальные роли авторов
    discipline: Optional[str] = None   # ключ из disciplines.yaml
    text: str                 # "[2026-10-21 14:03] starosta: ..."

class SearchHit(BaseModel):
    chunk_id: str
    chat: str
    text: str                 # не длиннее 1500 символов
    ts_from: ISO
    ts_to: ISO
    roles: list[Role]
    msg_ids: list[str]
    discipline: Optional[str] = None
    score: float              # после реранка, больше = лучше

class Answer(BaseModel):
    text: str
    sources: list[SearchHit]
    refused: bool = False     # True: "В материалах этого нет"
    prompt_version: str       # "answer_v1"

# ---------- роль 4 ----------
class DeadlineExtract(BaseModel):   # ответ LLM, только внутри tracker
    has_deadline: bool
    discipline: Optional[str] = None
    kind: Optional[Kind] = None
    task: Optional[str] = None
    due_text: Optional[str] = None
    action: Optional[Literal["new", "move", "cancel"]] = None
    fuzzy: bool = False
    confidence: float = Field(ge=0, le=1)

class Deadline(BaseModel):
    id: Optional[int] = None  # присваивает SQLite
    discipline: str
    kind: Kind
    task: str                 # "Лаб.2"
    due_at: Optional[ISO] = None     # None, если срок размытый
    due_text: str             # как написано: "до пятницы"
    fuzzy: bool = False
    status: Status = "active"
    source_msg: str           # id сообщения-источника
    confidence: float
    updated_at: Optional[ISO] = None
    attachments: list[AttachedFile] = []   # db заполняет при чтении

class DeadlineEvent(BaseModel):     # строка истории
    id: int
    deadline_id: int
    old_due: Optional[ISO]
    new_due: Optional[ISO]
    source_msg: str
    changed_at: ISO

class PendingItem(BaseModel):       # ждёт подтверждения человека
    id: int
    candidate: Deadline
    matched_id: Optional[int]        # на что похоже
    reason: Literal["low_confidence", "ambiguous_match", "no_match_for_move"]
    source_text: str                 # текст сообщения для показа
    created_at: ISO

class Report(BaseModel):            # результат process_new
    processed: int
    added: int
    moved: int
    cancelled: int
    pending: int
    skipped_prefilter: int
    failed: int

class Lesson(BaseModel):
    id: Optional[int] = None
    discipline: str
    lesson_type: LessonType
    start: ISO                # конкретное занятие, не шаблон
    end: ISO
    teacher: Optional[str] = None
    room: Optional[str] = None

class ScheduleImport(BaseModel):
    ok: bool
    lessons: list[Lesson]     # предпросмотр
    errors: list[str]         # "Строка 7: не найдена дисциплина ..."
    replaced: int             # сколько старых занятий заменено

# ---------- роль 5 ----------
class ToolCall(BaseModel):
    tool: str
    args: dict
    result_preview: str       # первые 300 символов
    duration: float           # секунды
    error: Optional[str] = None

class AgentResult(BaseModel):
    text: str
    sources: list[SearchHit] = []
    trace: list[ToolCall] = []
    pending_ids: list[int] = []      # что ждёт подтверждения из этого ответа

# ---------- роль 6 / все ----------
class DeadlineCard(BaseModel):      # всё для карточки задания
    deadline: Deadline        # внутри deadline.attachments
    history: list[DeadlineEvent]
    discussion: list[SearchHit]   # что говорили вокруг задания

class MessageContext(BaseModel):
    target: Message
    before: list[Message]
    after: list[Message]

class IndexStatus(BaseModel):
    chat: str
    messages: int
    period_from: ISO
    period_to: ISO
    last_processed: Optional[ISO]
    chunks: int
    deadlines: int

# ---------- для статьи (роли 1, 2) ----------
class LabelRecord(BaseModel):
    msg_id: str
    model_json: Optional[str] = None
    human_json: Optional[str] = None
    prompt_version: str
    model_name: str
```

### Окружение у каждого

1. Установить Python 3.11 или новее. Создать окружение: `python -m venv .venv`, активировать (Windows: `.venv\Scripts\activate`, Linux и macOS: `source .venv/bin/activate`).
2. Установить зависимости: `pip install -r requirements.txt`. Если нужного пакета нет, добавить его в `requirements.txt` в том же pull request.
3. Установить Ollama с официального сайта. Скачать модели: `ollama pull qwen3:8b` и `ollama pull bge-m3`. На ноутбуке с 8 ГБ памяти вместо 8B взять `qwen3:4b`.
4. Проверить: `ollama run qwen3:8b "привет"` отвечает, а `python -c "import ollama; print(len(ollama.embed(model='bge-m3', input=['тест']).embeddings[0]))"` печатает число (размер вектора).
