# Сравнение конфигураций поиска на реальных чатах

## Серверный прогресс и выгрузка

Дополнительное исследование цепочек запускается командой
`bash deploy/run_experiment.sh --suite threads`.
Это 8 вариантов × 82 вопроса = 656 выдач: пороги 0, 0.05, 0.1, 0.2, 0.3, 0.5,
40 кандидатов с реранжированием 30 при пороге 0.3 и вариант без реранкера.
У всех top_k=5. Перед замерами каждого варианта выполняется отдельный прогрев;
его время сохраняется отдельно. Сохраняются оценки и ID всех выданных кандидатов,
поэтому пороги можно дополнительно анализировать локально.
Это подбор настроек на уже просмотренной выборке, а не независимая проверка
обобщения. Для него не следует заявлять качество на новых чатах.

Актуальный генератор создаёт 82 вопроса (58 с ответом, 24 без ответа).
Некоторые вопросы проверяют разные факты из одних сообщений; это не 82 независимых события.
По умолчанию сравниваются 10 конфигураций: исходные четыре, окна 3 и 15,
окно 5 с 40 кандидатами/30 для реранкера, пороги 0 и 0.5, окно 5 без реранкера.
Метки предметов определяются один раз и одинаковы для всех вариантов.

На сервере запускайте в `tmux`, чтобы отключение SSH не прерывало работу:

```bash
tmux new -s experiment
bash deploy/run_experiment.sh
# Отсоединиться: Ctrl+B, затем D. Вернуться: tmux attach -t experiment
```

Скрипт печатает каталог `data/eval/run-<UTC-время>`. В другом SSH-сеансе:

```bash
tail -f data/eval/run-<UTC-время>/run.log
```

После каждого вопроса атомарно обновляются `results.json` и `results.zip`.
ZIP содержит текущие результаты, эталон и журнал; JSON включает конфигурации,
метки предметов и статус каждого варианта. При выходе обёртка создаёт также
`run-<UTC-время>.tar.gz` с версиями пакетов, коммитом и сведениями о GPU.
Частичные результаты доступны до окончания всего эксперимента.
На ноутбуке скачайте архив, подставив фактический каталог:

```bash
scp USER@SERVER:~/Ai_agent/data/eval/run-<UTC-время>/results.zip .
scp USER@SERVER:~/Ai_agent/data/eval/run-<UTC-время>.tar.gz .
```

Проверьте, что скачанный архив открывается, прежде чем останавливать арендованный сервер.
Повторный запуск создаёт новый каталог; автоматического продолжения с места остановки нет.

Эксперимент сравнивает поиск подтверждающих сообщений. Он **не измеряет качество ответа агента**: для этого нужны отдельная разметка ответов и прогон LLM. Все варианты используют один набор вопросов, одни и те же обезличенные сообщения, модель эмбеддингов и (кроме варианта без реранкера) одну модель реранкера.

## Данные и разметка

Положите обезличенные чаты в `data/clean/<chat>.jsonl`. Подготовьте `data/labels/search_gold.jsonl`: одна строка JSON на вопрос. Пример:

Для пробного запуска без реальных данных можно создать **отдельный полностью вымышленный корпус** командой `python -m scripts.make_search_experiment_chat`. Генератор создаёт один общий чат `synthetic_group` из 390 сообщений: темы трёх предметов перемешаны с бытовым общением, старыми слухами и ложными сроками. К нему прилагаются 82 эталонных вопроса; генератор не перезаписывает существующий эталон. Полученные на нём цифры проверяют работу экспериментального стенда, но не характеризуют качество на реальной переписке.

```json
{"query":"Когда перенесли ЛР2?","chat":"elektro","relevant_msg_ids":["elektro:1040"]}
{"query":"Какой срок у несуществующей ЛР99?","chat":"elektro","relevant_msg_ids":[]}
```

`relevant_msg_ids` содержит ID сообщений, в которых есть достаточное основание для ответа. Для вопроса без ответа укажите пустой список и обязательный `chat`. Подготовьте 30–50 вопросов до просмотра выдачи; включите короткие ответы, переносы, разные дисциплины и 5–10 вопросов без ответа. Для достоверности разметьте сообщения вручную; не используйте выдачу системы как эталон. Не публикуйте тексты или ID из частного корпуса.

## Запуск

Требуются установленные зависимости проекта, доступная Ollama с `models.embed` и, если включена классификация предметов, `models.llm`; при включённом реранкере также нужна модель `models.reranker`. Классификация предметов выполняется один раз перед сравнением вариантов. Для сравнения только параметров поиска зафиксируйте `retrieval.subject_model_enabled` одинаково для всех вариантов. Из корня репозитория:

```bash
python -m eval.search_config_experiment --gold data/labels/search_gold.jsonl \
  --out data/eval/search_config_results.json
```

Скрипт сравнивает `window_10_rerank`, `window_5_rerank`, `thread_rerank` и `window_10_no_rerank`. Для каждого варианта создаётся временный индекс. Результат содержит фактический конфиг, число чанков, суммарные метрики, оценку и ID найденного фрагмента по каждому вопросу, время поиска. Исходные чаты, индексы и вывод лежат вне Git.

## Интерпретация

- **hit@k**: доля вопросов с ответом, для которых хотя бы одно размеченное сообщение попало в выдачу после применимого порога.
- **MRR**: среднее обратное место первого релевантного фрагмента среди вопросов с ответом.
- **false_accept_rate**: доля вопросов без ответа, для которых поиск всё же вернул фрагменты. Без реранкера текущая система не применяет `min_score`, поэтому этот вариант не сопоставим по отказам без отдельного порога.
- **mean_search_seconds**: среднее время собственно поиска; время построения индекса сюда не входит.

Сначала сравните hit@k и MRR. Затем отдельно посмотрите ошибки отказа и время. Не выбирайте вариант по одному показателю и не называйте близкие результаты доказанным превосходством на маленькой выборке. После выбора конфигурации оцените финальные ответы агента на том же наборе отдельным экспериментом.
