# Анализатор учебных чатов: описание проекта

*Локальный ИИ-агент с RAG и MCP для учебных чатов*

## 1. Коротко о проекте

**«Анализатор учебных чатов»** это локальный ИИ-агент, который читает учебные чаты (экспорт Telegram в HTML), отвечает на вопросы по ним со ссылками на источники, самостоятельно находит в переписке дедлайны и домашние задания, отслеживает их переносы, прикрепляет к каждому заданию файлы из чата (методички, шаблоны, условия) и сопоставляет сроки с учебным расписанием. Всё работает локально, без облачных сервисов третьих лиц: на ноутбуке или (рекомендуется) на собственном сервере с GPU, куда вынесено всё тяжёлое (модель, реранкер, индекс, база, интерфейс), а пользователи открывают приложение в браузере через SSH-туннель (`docs/server_setup.md`). Модель до 8 миллиардов параметров на CPU и крупнее на GPU.

Проект делается для кейс-чемпионата по курсу Ю. Е. Гапанюка (вариант А: индексация, RAG, MCP-инструменты) и с первого дня строится так, чтобы затем лечь в основу статьи по цифровой гуманитаристике о языке дедлайнов в учебной коммуникации.

| Параметр | Значение |
|---|---|
| Тип системы | Локальный ИИ-агент с RAG и MCP-инструментами |
| Предметная область | Учебные чаты студенческой группы: объявления, дедлайны, вопросы, переносы |
| Данные | 2–3 обезличенных чата за 1–3 месяца (HTML-экспорт Telegram вместе с вложенными документами) и файл расписания (.ics или Excel) |
| Модель | Qwen3 8B (запасной вариант 4B; на сервере с GPU возможна крупнее, выбор по замерам), эмбеддинги bge-m3, всё через Ollama (локальную или на своём сервере) |
| Интерфейс | Веб-приложение на Streamlit: чат, календарь дедлайнов с карточкой задания, расписание, источники |
| Команда | 5–6 человек, 6 ролей |

## 2. Центральная идея: карточка задания

Всё в системе строится вокруг **карточки задания**. Для каждого дедлайна, найденного в чате, система собирает: срок (как написан и в виде даты), статус, историю переносов со ссылками на сообщения, **прикреплённые файлы** (то, что прислали вместе с заданием) и **обсуждение** (сообщения, где объясняли требования и уточняли условия). Трекер заполняет первые три части, поиск (RAG) заполняет последнюю. Поэтому RAG здесь не отдельная приставка, а часть карточки.

## 3. Какую проблему решает

Важная учебная информация тонет в потоке сообщений: срок сдачи лабораторной объявили три недели назад, потом перенесли, потом уточнили в ответе на чужое сообщение. Найти актуальную версию вручную долго, а ошибка стоит пропущенного дедлайна. Расписание при этом хранится отдельно, и фразы вроде «сдаём на следующей паре» нельзя превратить в дату без него.

Система берёт на себя три задачи: быстро найти нужное в чатах и показать, откуда взят ответ; сама вести актуальный список дедлайнов с историей переносов; связать «на следующей паре» с реальной датой по расписанию.

## 4. Что умеет система

| Функция | Что делает пользователь и что получает |
|---|---|
| Ответы на вопросы по чатам (RAG) | Спрашивает «Когда сдавать Лаб.2?» или «Что говорили про перенос рубежки?». Получает ответ только по найденным сообщениям, со списком источников (дата, роль автора, фрагмент) и кнопкой «Показать в чате» |
| Честное «не знаю» | Если в чатах ответа нет, система говорит «В материалах этого нет» и не выдумывает |
| Автоматический поиск дедлайнов | Система читает новые сообщения и вытаскивает из них задание, дисциплину и срок. Размытые сроки («на неделе») помечает отдельно |
| Отслеживание переносов | Если срок изменился, запись обновляется, а прежний срок остаётся в истории с ссылкой на сообщение-основание. Цепочка вида «20.10 → 28.10 → 05.11» |
| Подтверждение сомнительного | Когда система не уверена или не может понять, к какому заданию относится перенос, запись попадает в очередь. Решает человек кнопками «Подтвердить» и «Отклонить» |
| Загрузка расписания | Загружается файл .ics или Excel; перед записью показываются распознанные занятия и ошибки. Срок «на следующей паре по электротехнике» превращается в дату по расписанию |
| Файлы к заданиям | К дедлайну автоматически прикрепляются файлы из чата: из того же сообщения, от того же автора рядом по времени и из ответа на сообщение. При переносе файлы остаются, новые добавляются. Содержимое файлов не анализируется |
| Обсуждение вокруг задания | Для карточки задания поиск находит сообщения с требованиями, уточнениями и обсуждением переноса, не считая само объявление о сроке |
| Карточка задания и календарь | Занятия и дедлайны на одном календаре (у заданий с файлами значок скрепки), фильтры; в карточке срок, статус, история переносов, материалы (открыть файл, показать сообщение) и «Что говорили» |
| Подсветка | В тексте сообщения выделены срок, задание и дисциплина |
| Агентный режим | Агент сам выбирает инструмент (поиск по чатам, список дедлайнов, файлы заданий, расписание, обработка новых сообщений), показывает, что вызывал, и не более пяти шагов на вопрос |
| Аналитика (по желанию) | Тепловая карта активности чата, статистика сообщений по ролям, граф связей заданий и сообщений |

### Как RAG и трекер работают вместе

| Вопрос пользователя | Что делает агент |
|---|---|
| «Когда сдавать Лаб.2?» | Берёт срок из базы дедлайнов |
| «Какие материалы к Лаб.2?» | Берёт файлы карточки (`get_attachments`) |
| «Что нужно в отчёте по Лаб.2?» | Ищет по чату (RAG), добавляет методичку из карточки |
| «Почему перенесли рубежку?» | Берёт историю переноса и ищет сообщения вокруг него |
| «Что на этой неделе?» | Дедлайны плюс расписание |
| Дедлайн не нашёлся автоматически | Поиск находит кандидатов, человек подтверждает |

## 5. Как это устроено

Система состоит из пяти слоёв. Слои соединены строго описанными форматами данных (документ «Контракты данных»), поэтому разные люди пишут их параллельно.

```
Экспорт Telegram (HTML + files/)   Расписание (.ics / .xlsx)
         |                        |
   [1] Данные                     |
   парсер (+вложения),            |
   обезличивание                  |
         |                        |
   сообщения (JSONL)              |
      |            |              |
 [2] Индекс    [3] Трекер <-------+
 чанки, поиск   предфильтр, модель,
 (RAG)          даты, переносы, файлы, SQLite
      |            |
      +-----+------+
            |
   [4] MCP-сервер и агент
   инструменты, цикл выбора
            |
   [5] Интерфейс (Streamlit)
   чат, календарь, расписание
```

### 5.1. Слой данных

Парсер читает файлы `messages.html`, `messages2.html` и так далее, определяет автора (включая подряд идущие сообщения без имени), время, ответы на сообщения, пересланное и вложения-документы (папка `files/`). Затем сообщения обезличиваются: имена заменяются постоянными метками (`STAROSTA`, `TEACHER_1`, `STUDENT_7`), телефоны и ссылки удаляются. На выходе единый формат `Message`.

### 5.2. Слой поиска (RAG)

Сообщения группируются в чанки (окно из нескольких подряд идущих сообщений, чтобы сохранить контекст: «до пятницы» без вопроса ничего не значит). Для чанков считаются эмбеддинги (bge-m3, хранилище Chroma) и строится лексический индекс BM25 с лемматизацией. Запрос ищется обоими способами, результаты объединяются методом RRF и пересортировываются реранкером. Модель получает только лучшие фрагменты и отвечает строго по ним.

### 5.3. Слой трекера

Дешёвый предфильтр отсеивает сообщения без признаков срока, чтобы не гонять модель впустую. Остальные идут в модель, которая возвращает JSON по схеме: есть ли дедлайн, какая дисциплина, какое задание, как записан срок, это новый срок, перенос или отмена. Даты вычисляет код, а не модель (пакет dateparser и расписание). Дальше запись сопоставляется с уже известными заданиями; новые добавляются, переносы обновляют срок и пишут историю, сомнительное ждёт подтверждения человека. К дедлайну прикрепляются файлы: из того же сообщения, от того же автора в пределах нескольких минут и из ответа на сообщение. Хранится всё в SQLite. Для карточки задания поиск (слой RAG) находит «обсуждение»: сообщения с требованиями и уточнениями.

### 5.4. MCP-сервер и агент

Возможности системы оформлены как набор MCP-инструментов (поиск по сообщениям, чтение новых, список дедлайнов, добавление и обновление, расписание, файлы задания, обработка новых сообщений). Агент получает вопрос, выбирает инструмент, смотрит результат и решает, звать ли ещё один. Каждый вызов записывается в трассу. Если модель плохо выбирает инструменты, включается запасной режим с маршрутизацией правилами.

### 5.5. Интерфейс

Streamlit-приложение с четырьмя вкладками: «Чат», «Дедлайны» (календарь и карточка задания с файлами и обсуждением), «Расписание», «Источники». Интерфейс не содержит логики: он обращается к остальным слоям через один слой-провайдер, у которого есть режим с заглушками (чтобы разрабатывать интерфейс, пока остальное не готово) и режим с настоящими модулями.

## 8. Данные, приватность и этика

- Согласие участников чатов на использование сообщений получено.
- Исходные экспорты хранятся только у роли 2 локально и никогда не попадают в репозиторий, общие чаты или на сервер (`data/` в `.gitignore`).
- На сервер команды (он свой, облачные сервисы третьих лиц не используются) кладутся только обезличенные данные; доступ по SSH-ключам, без открытых портов Ollama и Streamlit в интернет (`docs/server_setup.md`, раздел 7).
- Остальные участники работают с обезличенными данными и синтетическим мини-чатом из тестов.
- Имена заменяются постоянными метками, телефоны, адреса и ссылки удаляются; для статьи сохраняются только роли и метки.
- Вложения остаются только на локальном диске (`data/raw/<чат>/files/` в `.gitignore`); фамилии в названиях файлов заменяются; содержимое файлов может содержать личные данные, поэтому файлы не пересылаются и не публикуются.
- В промпты для ИИ-помощников реальные сообщения не вставляются.

## 9. Как проверяется качество

Размечается эталонный набор из 30–50 сообщений (20% двумя людьми, согласованность считается по каппе Коэна). По нему измеряются:

- **Трекер:** точность, полнота и F1 нахождения дедлайнов; доля верно вычисленных дат; доля верно распознанных переносов.
- **Файлы:** точность и полнота привязки файлов к дедлайнам (доля верно прикреплённых и доля найденных нужных), доля ложных привязок.
- **Поиск:** hit@5 и MRR на 20–30 вопросах с эталоном, доля честных «нет» на вопросах без ответа, время поиска.
- **Обсуждение:** доля заданий, у которых блок «Что говорили» содержит полезное сообщение (оценка вручную).
- **Агент:** доля верного выбора инструмента и параметров (отдельно для вопросов про сроки, файлы и обсуждение), время ответа, доля случаев, когда сработал запасной режим.
- **Интерфейс:** проверка удобства на человеке не из команды (время и места, где он замешкался).

## 11. Границы проекта

В этой версии намеренно не делаются: подключение почты, локальных папок и дисков с учебными материалами (файлы берутся только из самих чатов), анализ содержимого файлов (привязка только по связям сообщений), автоматическая проверка лабораторных, работа с изображениями и голосовыми сообщениями, облачные модели сторонних провайдеров (модель работает на своём сервере или ноутбуке). Ограничения модели 8B (медленная работа на слабом ноутбуке, иногда ошибки в инструментах) учитываются запасными режимами и порогами уверенности; тяжёлая работа вынесена на сервер.

## 12. Развитие под статью по цифровой гуманитаристике

Проект собирается так, чтобы потом стать исследованием языка дедлайнов в учебной коммуникации. Основа для этого закладывается сразу:

- **Корпус:** обезличенные сообщения в едином формате с ролями авторов (староста, преподаватель, студент), датами и вложениями. Дополнительный слой: какие файлы сопровождают какие выражения сроков.
- **Схема аннотации:** руководство по разметке сроков, переносов, размытых и событийных формулировок («на следующей паре»), примеры и правила спорных случаев.
- **Локальная модель как инструмент аннотации:** ответ модели и решение человека хранятся отдельно (`LabelRecord`), с версией промпта и названием модели, что позволяет сравнивать и воспроизводить.
- **Метрики:** согласованность аннотаторов, качество модели против человека, ошибки по типам выражений.
- **Этика:** согласие, обезличивание, правила хранения и публикации корпуса.

Тогда статья описывает язык дедлайнов и метод его исследования локальной моделью, а система служит экспериментальной установкой и практическим применением.

## 13. Основные риски

| Риск | Что делаем |
|---|---|
| Модель 8B слишком медленная | Переходим на 4B, сокращаем контекст, включаем порог релевантности, чтобы не вызывать модель впустую |
| Модель плохо вызывает инструменты | Запасной режим: маршрутизация правилами, модель только формулирует ответ |
| Файлы не выгрузились или не нашлись при экспорте | Проверить экспорт с галочкой «Файлы» на первом чате; вложения без файла не создаются; интерфейс показывает «Файл не найден» |
| Форматы между модулями не сходятся | Единый контракт данных, изменения только через pull request с пометкой `contract-change` |
| Данные попали в репозиторий | Игнорирование `data/`, ревью, работа на синтетических данных; при утечке сразу убрать из истории и сообщить команде |
| Роль не успевает | Перераспределяем: заглушки и контракты позволяют другим ролям подхватить часть работы |
