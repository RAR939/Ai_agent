# Структура HTML-экспорта Telegram Desktop

**Задача:** 2.2 «Изучение структуры HTML».  
**Источники:** два локальных экспорта, `IU5-31B` (`messages.html`, `messages2.html`, `messages3.html`) и `IU5` (`messages.html`, `messages2.html`).  
**Правило приватности:** ниже приведены **только синтетические примеры** с вымышленными именами, текстами, ссылками и именами файлов. Реальные сообщения и названия файлов не воспроизводятся. Код HTML сокращён до существенных элементов; `...` обозначает пропущенную служебную разметку. Примеры показывают обнаруженные варианты структуры, но не являются буквальными копиями исходных фрагментов.

## 1. Результаты исследования двух экспортов

| Признак | `IU5-31B` | `IU5` |
|---|---:|---:|
| Файлов `messages*.html` | 3 | 2 |
| Блоков `div.message` | 2455 | 1510 |
| `div.message.default` | 2362 | 1422 |
| `div.message.service` | 93 | 88 |
| `div.message.default.joined` | 675 | 457 |
| Сообщений с `div.forwarded.body` | 123 | 32 |
| Блоков `.media_file` | 49 | 32 |
| Блоков `.media_file` со ссылкой `href="files/..."` | 43 | 24 |
| Блоков `.media_file` без ссылки `href` | 6 | 8 |

**Вывод:** базовые HTML-классы и расположение полей совпадают в обоих чатах. Отличаются количество сообщений, варианты контента и частота вложений. У обоих экспортов есть сообщения с недоступными файлами; это не повод создавать `AttachedFile`. Некоторые `media_file` указывают на изображения или архивы, а не на документы.

## 2. Карта разметки и правила извлечения

| Данные | Где находятся | Правило для парсера |
|---|---|---|
| Сообщение | `div.message.default[id^="message"]` | `id="message1042"` → `IU5-31B:1042`. Служебные сообщения обрабатывать отдельно. |
| Автор сообщения | непосредственный дочерний `div.from_name` внутри внешнего `div.body` | Имя — исходное, до этапа анонимизации не выводить в отчёты/логи. |
| Последовательное сообщение | класс `joined` у `div.message` | Имени автора на основном уровне нет. Наследовать автора из предыдущего сообщения того же чата; учитывать переход между HTML-файлами. |
| Время | `div.pull_right.date.details`, атрибут `title` | Фактический формат: `DD.MM.YYYY HH:MM:SS GMT+03:00`. Текст блока — `HH:MM`, его недостаточно. |
| Текст | `div.text` внутри основного `div.body` **или** внутри `div.forwarded.body` | Извлекать видимый текст, сохраняя логические переносы из `<br>`; не смешивать с именами/служебными полями. |
| Ответ | `div.reply_to.details > a[href]` | Встречаются ссылки `#go_to_messageN`, `messages.html#go_to_messageN`, `messages2.html#go_to_messageN`. Извлекать конечный `N`; связь может указывать за пределы экспорта. |
| Пересылка | вложенный `div.forwarded.body` | Это признак `forwarded=True`; внутренний `from_name` обозначает **источник пересылки**, а не автора текущего сообщения. |
| Документ, файл есть | `div.media_wrap.clearfix > a.media_file[href^="files/"]` | Название внутри `div.title.bold`, показанный размер внутри `div.status.details`, относительный путь — из `href`. Фактический размер в байтах брать с диска. |
| Файл не выгружен | `div.media_wrap.clearfix > div.media_file` без `href` | Внутри могут быть `title.bold`, `description`, `status.details`. **Не** создавать `AttachedFile`. |
| Служебное событие | `div.message.service > div.body.details` | Не имеет стандартной структуры имени и даты обычного сообщения. Не подставлять фиктивные время/автора. |
| Редактирование | отдельный маркер не подтверждён | Не выводить статус редактирования из текста или времени; см. раздел 4. |

### Время

Реальный формат атрибута `title` в обоих экспортах: `DD.MM.YYYY HH:MM:SS GMT+03:00`, например, **синтетическое значение** `21.10.2026 14:03:00 GMT+03:00`. При формировании `Message.ts` результат должен быть `2026-10-21T14:03:00+03:00`. Для Python 3.11 соответствует форматная строка `%d.%m.%Y %H:%M:%S GMT%z`. Время без `+03:00` запрещено. Видимый текст `14:03` не должен быть источником полной даты.

### Ответы и вложенные блоки

В `reply_to details` часто есть ссылка даже в сообщениях, которые визуально воспринимаются как обычные сообщения. Проверено наличие **как локальных, так и межфайловых ссылок**. Нельзя считать само наличие класса достаточным основанием для какой-либо дополнительной интерпретации; извлекать конкретный `href`. У пересланных сообщений `reply_to` иногда расположен внутри `forwarded.body` и может описывать исходный контекст пересылки. Не смешивать его с ответом, находящимся непосредственно во внешнем `body`.

Селекторы желательно применять от **внешнего** `div.message > div.body` с проверкой непосредственных дочерних элементов: внутри `.forwarded.body`, `.media_file .body` и реакций могут повторяться классы `body`, `from_name`, `date`.

## 3. Синтетические HTML-примеры обнаруженных разновидностей

### 3.1. Обычное сообщение с именем автора

```html
<div class="message default clearfix" id="message1042">
  <div class="pull_left userpic_wrap">...</div>
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 14:03:00 GMT+03:00">14:03</div>
    <div class="from_name">Мария Примерова</div>
    <div class="text">Завтра будет консультация.</div>
  </div>
</div>
```

### 3.2. Следующее сообщение того же автора (`joined`)

```html
<div class="message default clearfix joined" id="message1043">
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 14:04:00 GMT+03:00">14:04</div>
    <div class="text">Начало в 15:00.</div>
  </div>
</div>
```

На верхнем уровне нет `from_name`; автор наследуется от предыдущего сообщения. Не искать автора по произвольному вложенному `from_name` (он может относиться к пересылке).

### 3.3. Ответ на сообщение

```html
<div class="message default clearfix" id="message1050">
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 15:00:00 GMT+03:00">15:00</div>
    <div class="from_name">Иван Условный</div>
    <div class="reply_to details">
      <a href="messages.html#go_to_message1042">Ответ на предыдущее сообщение</a>
    </div>
    <div class="text">Спасибо, понятно.</div>
  </div>
</div>
```

Тот же атрибут `href` может иметь вид `#go_to_message1042`. В контракте `Message.reply_to = "IU5-31B:1042"`, даже если целевого сообщения в выгрузке нет.

### 3.4. Пересланное сообщение

```html
<div class="message default clearfix" id="message1051">
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 15:05:00 GMT+03:00">15:05</div>
    <div class="from_name">Иван Условный</div>
    <div class="pull_left forwarded userpic_wrap">...</div>
    <div class="forwarded body">
      <div class="from_name">Персонаж Альфа
        <span class="date details"
              title="20.10.2026 18:00:00 GMT+03:00">...</span>
      </div>
      <div class="text">Пример пересланного объявления.</div>
    </div>
  </div>
</div>
```

`forwarded=True`; основным автором остаётся внешний `from_name`.

### 3.5. Сообщение со ссылкой и форматированием

```html
<div class="message default clearfix" id="message1052">
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 15:10:00 GMT+03:00">15:10</div>
    <div class="from_name">Мария Примерова</div>
    <div class="text">
      <strong>Материалы занятия:</strong><br>
      <a href="https://example.org/materials">пример ссылки</a>
    </div>
  </div>
</div>
```

В проверенных экспортах обнаружены `<a>`, `<strong>`, `<em>`, `<u>`, `<br>`. Для `Message.text` важен читаемый текст; HTML-теги не должны попадать в итоговое поле как разметка.

### 3.6. Файл с подписью

```html
<div class="message default clearfix" id="message1053">
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 15:15:00 GMT+03:00">15:15</div>
    <div class="from_name">Мария Примерова</div>
    <div class="media_wrap clearfix">
      <a class="media clearfix pull_left block_link media_file"
         href="files/example_lab.pdf">
        <div class="fill pull_left">...</div>
        <div class="body">
          <div class="title bold">example_lab.pdf</div>
          <div class="status details">120 KB</div>
        </div>
      </a>
    </div>
    <div class="text">Шаблон для выполнения лабораторной.</div>
  </div>
</div>
```

`href` — путь относительно корня экспорта `data/raw/<chat_id>/`; `title.bold` — имя для отображения (позже обезличивается); `status.details` — показанный размер, например в `KB` или `MB`. Для `AttachedFile.size_bytes` использовать размер существующего файла на диске, а не округлённую строку из HTML.

### 3.7. Файл без подписи

```html
<div class="message default clearfix joined" id="message1054">
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 15:16:00 GMT+03:00">15:16</div>
    <div class="media_wrap clearfix">
      <a class="media clearfix pull_left block_link media_file"
         href="files/example_notes.docx">
        <div class="fill pull_left">...</div>
        <div class="body">
          <div class="title bold">example_notes.docx</div>
          <div class="status details">90 KB</div>
        </div>
      </a>
    </div>
  </div>
</div>
```

В результате обработки документа без подписи необходимо заполнить `Message.text = "[файл: <обезличенное имя>]"`; пустой текст недопустим.

### 3.8. Вложение, которое не было выгружено

```html
<div class="message default clearfix" id="message1055">
  <div class="body">
    <div class="pull_right date details"
         title="21.10.2026 15:20:00 GMT+03:00">15:20</div>
    <div class="from_name">Иван Условный</div>
    <div class="media_wrap clearfix">
      <div class="media clearfix pull_left media_file">
        <div class="fill pull_left">...</div>
        <div class="body">
          <div class="title bold">example_large.pdf</div>
          <div class="description">[описание недоступного вложения]</div>
          <div class="status details">25 MB</div>
        </div>
      </div>
    </div>
  </div>
</div>
```

**Фактическое отличие:** у недоступного вложения используется `div.media_file` **вместо** `a.media_file[href]`. В обоих экспортах такие блоки есть. Поле `AttachedFile` не формировать; нельзя придумывать `path` или `size_bytes`. Приведённый текст `description` — заглушка, не цитата из экспорта.

### 3.9. Служебное сообщение

```html
<div class="message service" id="message-100">
  <div class="body details">Вымышленный участник вступил в группу</div>
</div>
```

Служебные блоки могут иметь отличный от `messageN` вид `id`; обычные `from_name`, `div.pull_right.date.details` отсутствуют. Не преобразовывать их в обычный `Message` путём выдумывания полей. Описать политику пропуска на этапе 2.3.

### 3.10. Отредактированное сообщение — НЕ ПОДТВЕРЖДЕНО

При автоматическом обследовании обоих экспортов **не обнаружен достоверный HTML-маркер редактирования** (например, отдельный `edited`-класс у сообщения). Поэтому реальный образец разметки отредактированного сообщения не приводится: добавлять предполагаемый HTML как фактический было бы ошибкой. Требуется вручную найти известное отредактированное сообщение в Telegram и сравнить его HTML после экспорта, либо отметить, что эта информация экспортом не представлена.

## 4. Нюансы, важные для `parse_export()`

1. **Порядок страниц:** разбирать `messages.html`, затем `messages2.html`, `messages3.html` и т. д. по числовому суффиксу; учитывать наследование автора `joined` между страницами в одном чате.
2. **Идентификаторы:** для обычного `id="messageN"` формировать строго `<chat_id>:N`, например `IU5:1042`. `Message.src` — `<файл HTML>#messageN`, например `messages2.html#message1042`.
3. **Ответы:** встречаются внутренние `#go_to_messageN` и ссылки в другие HTML-страницы `messages.html#go_to_messageN`; сохранить целевой идентификатор даже без присутствующего исходного сообщения. `reply_to` внутри `forwarded.body` не приравнивать автоматически к ответу текущего сообщения.
4. **Поля из вложенных элементов:** `from_name`, `body`, `date.details`, `reply_to.details` могут повторяться во вложенной пересылке и описании файла. Нельзя брать первый найденный класс по всему поддереву без учёта вложенности.
5. **Документы:** класс `media_file` не гарантирует, что это документ. В экспортируемых файлах с этим классом есть форматы изображений и архивов; проверять тип и наличие файла на диске. Не включать фотографии, картинки и прочие недокументные медиа в `attachments`.
6. **Имя документа:** `title.bold` — исходное имя, которое может содержать персональные данные; показывать и сохранять в `AttachedFile.name` только обезличенный вариант. `AttachedFile.path` сохраняет реальный относительный путь для локального доступа, но не должен попадать в подсказки ИИ или публичные отчёты.
7. **Нет подписи:** для существующего документа без текста обязательно создавать непустой `Message.text` по контрактному шаблону `[файл: <обезличенное имя>]`.
8. **Служебные и неприменимые сообщения:** `service` не обеспечивает обязательные поля обычного `Message`. Никаких выдуманных значений для автора, времени или роли; отдельно зафиксировать пропуск при реализации парсера.
9. **Время:** считывать `title`, учитывать `GMT+03:00`, приводить к ISO 8601 с `+03:00`. Не использовать только показанное `HH:MM`.
10. **Секретность:** реальные HTML, имена пользователей и исходные имена файлов не добавлять в репозиторий, примеры, логи и промпты. Документация содержит только синтетические значения.

## 5. Отличия и неопределённости

- **Совпадает:** контейнер обычного сообщения, классы времени, ответа, пересылки, `joined`, служебных событий, вложений. В обоих чатах найдены скачанные и отсутствующие вложения.
- **Различается:** количество страниц, сообщений, пересылок, вложений, а также встречающиеся расширения файлов. Отдельный HTML-парсер под каждый из двух чатов **не нужен**.
- **Не подтверждено:** отдельная разметка, по которой можно достоверно определить редактирование. Требуется целевой ручной тест на известном отредактированном сообщении.
- **За рамками 2.2:** реализация `parse_export()`, обезличивание, заполнение `Message`/`AttachedFile`, тесты функций — это последующие задачи, контракт не меняется.
