# Архитектура

## Слои и поток данных

```
Экспорт Telegram (HTML + files/)            Расписание (.ics / .xlsx)
        │ [1] парсер, обезличивание (роль 2)          │
   data/clean/<чат>.jsonl  (Message)                  │
        ├──────────────────────┐                      │
 [2] индекс и поиск (роль 3)   │   [3] трекер (роль 4) ◄┘
     чанки, Chroma, BM25,      │       предфильтр → модель → даты → сопоставление → файлы
     реранкер, ответ           │       SQLite: дедлайны, история, очередь, файлы, расписание
        └──────────┬───────────┘
        [4] MCP-сервер и агент (роль 5): 9 инструментов, цикл выбора, не более 5 шагов
                   │
        [5] интерфейс Streamlit (роль 6): Дедлайны, Чат, Расписание, Источники
```
Слои соединены только форматами из `docs/contracts.md` (`src/schemas.py`). Центральная идея: **карточка задания**
(срок, история, файлы, обсуждение): трекер заполняет первые три части, поиск четвёртую.

## Модули

| Что | Где | Роль |
|---|---|---|
| Схемы данных, проверка времени `+03:00` | `src/schemas.py` | 1 |
| Конфиг, дисциплины и их алиасы (по леммам) | `src/config.py`, `config/*.yaml` | 1 |
| Клиент Ollama (адрес, токен, таймаут) | `src/llm.py` | 1 |
| Парсер HTML, обезличивание (**ещё нет**), хранилище сообщений (заглушка) | `src/ingest/` | 2 |
| Чанкинг, эмбеддинги, поиск, ответ, обсуждение задания | `src/index/` | 3 |
| База, расписание, предфильтр, извлечение, даты, сопоставление, файлы, конвейер, напоминания | `src/tracker/` | 4 |
| MCP-инструменты, агентный цикл, промпты агента | `src/mcp_server.py`, `src/agent.py`, `config/prompts/` | 5 |
| Интерфейс, провайдер данных, карточка, подсветка, пароль | `ui/` | 6 |
| Оценка, разметка эталона | `eval/` | 1, 4 |
| Проверка окружения | `scripts/check_env.py` | 1 |

Слой **провайдера** (`ui/provider.py`): интерфейс не содержит логики, а ходит через `Provider`. `MockProvider` отдаёт выдуманные данные,
`RealProvider` вызывает настоящие модули; выбор по `ui.use_mock`.

## Что происходит при вопросе в чате
1. Интерфейс вызывает `Provider.ask` → `run_agent` (`src/agent.py`).
2. Агент запускает MCP-сервер подпроцессом (`python -m src.mcp_server`, окружение передаётся) и получает список инструментов.
3. В модель (`llm.chat`) уходит системный промпт (`agent_v2` с сегодняшней датой), история и вопрос. Модель просит вызвать инструмент:
   `list_deadlines`, `get_schedule`, `get_attachments`, `search_messages` и т. д. (`docs/mcp_tools.md`).
4. Сервер выполняет инструмент настоящим модулем, результат JSON возвращается модели; цикл повторяется не более `agent.max_steps` раз.
5. Ответ, источники (`SearchHit`), трасса вызовов (`ToolCall`) и `pending_ids` (записи, ждущие подтверждения) возвращаются в интерфейс;
   трасса пишется в `logs/agent_trace.jsonl` с версией промпта.
Если модель плохо выбирает инструменты, включается запасной режим `agent.mode: rules` (выбор по ключевым словам).

## Что происходит при «Обработать новые сообщения»
`tracker.pipeline.process_new(chat)`: для каждого необработанного сообщения по времени → **предфильтр** (ключевое слово и признак времени,
без модели) → **модель** (`extract`, JSON `DeadlineExtract`, срок дословно) → **даты** (`dates.resolve_due`, считает код, а не модель; «на следующей паре» по расписанию)
→ **сопоставление** (`match.apply_candidate`: новый, перенос с историей, отмена, очередь подтверждения при низкой уверенности или неоднозначности)
→ **файлы** (`attach.collect_files`: из того же сообщения, от того же автора рядом по времени, из ответа). Повторный запуск ничего не меняет.

## Что происходит при индексации и поиске
`index.build.reindex(chat)`: сообщения → чанки (окно 10 с шагом 5, до 1800 символов) → эмбеддинги `bge-m3` в Chroma + лексический индекс BM25
с лемматизацией. `index.search.search`: оба ранжирования → слияние RRF → реранкер (`bge-reranker-v2-m3`, если включён) → фрагменты с фильтрами
(чат, дисциплина, даты, роль). Порог `retrieval.min_score` применяется только к оценкам реранкера. Реранкер, Chroma и BM25 держатся в памяти процесса.

|---|---|---|

| Индекс | `data/chroma/`, `data/index_chunks.jsonl`, `data/bm25.pkl`, `data/index_state.json` | нет |

| Синтетические данные для тестов и демонстрации | `tests/fixtures/` | да |

## Режимы запуска
1. **Всё на сервере** (рекомендуется): Streamlit, агент, трекер, индекс, реранкер, база и Ollama на сервере с GPU; пользователь открывает браузер через
   SSH-туннель. Общие данные для всей команды. См. `docs/server_setup.md`.
2. **Приложение на ноутбуке, Ollama на сервере**: те же модули у каждого локально, к серверу ходят только за моделью (`models.host`, `OLLAMA_HOST`).
3. **Всё на ноутбуке**: локальная Ollama (`qwen3:8b` или `4b`), без интернета.

## Принципы
- **Контракт неприкосновенен**: форматы только через `src/schemas.py`; изменения отдельным PR `contract-change`.
- **Время** всегда строка ISO 8601 с `+03:00`; даты считает код, модель только достаёт факты.
- **Настройки** в `config/*.yaml` (локальные значения в `config.local.yaml`), секреты только в окружении.
- **Данные чатов не попадают в git**; для тестов только синтетический мини-чат. На сервер идут только обезличенные данные.
- **Модель всегда подменяема**: тесты не требуют Ollama (`src.llm.chat` подменяется), сквозные тесты запускают настоящий MCP-сервер.
- Ответ модели и решение человека хранятся раздельно (`LabelRecord`), с версией промпта и названием модели (задел под статью).
